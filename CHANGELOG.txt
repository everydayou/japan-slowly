# Japan Slowly — Changelog

Full round-by-round history. PROJECT-CONTEXT.txt is the current-state snapshot meant to be read every chat; this file is the detailed archive, read only when you need the "why" behind something older than the last round or two.

## ROUND 41 — 2026-09-20 (Copenhagen card only after Day 10 opens)

- The Copenhagen card showed while everything was locked because old test progress for Day 10 was still saved on the phone. `copenhagenOpen()` now also requires Day 10 itself to be open, so left-over progress cannot reveal it. `render()` clamps `stackIndex` to `deckLast()` so a saved position on the hidden card falls back to Day 10.
- Guide Mode never locks a day that the calendar has already opened (`dayReached(n) || chain`), so switching Guide Mode on during the trip only adds, never removes.
- Note: progress made while testing in Guide Mode is the same progress the real trip uses. Use "Guide · reset from this day" on Day 1 before leaving to clear everything.

## ROUND 36 — 2026-09-20 (real locks, Guide Mode override, live weather)

- TEST_MODE is gone. Real locking: a day opens at 00:00 Japan time (UTC+9, computed from the clock, not the phone's time zone) on its own date (Day 1 = 25 Sep); stays follow their `unlockDay`; a chapter with `gate:{time}` (Pasela, 20:00) shows "Not yet. Fetched on open, when the app returns to the foreground, when the connection comes back and every 30 minutes; the last good answer is kept in localStorage (`japanSlowlyWeather_v1`) so it works offline. The hard-coded `weather` per day stays as the fallback and is labelled "Typical weather for this time of year"; live data is labelled "Live forecast, updated ...". `sw.js` no longer intercepts api.open-meteo.com. ## ROUND 25 — 2026-09-17
New chat session, opened by reading PROJECT-CONTEXT.txt as instructed. The user reported the standalone/Safari bottom-gap and sheet-crop bugs were still happening (three screenshots: the standalone home screen showing a visible gap under the tabbar pill, the round-24 debug panel's own readout from that same standalone launch, and the About sheet showing its content cut off partway down with dead space below). Also asked to disable pinch/double-tap zoom.

**Root cause, found by reading the code rather than guessing again.** Rounds 20-24 correctly diagnosed that a `position:fixed` element's containing block on iOS Safari can resolve against the browser's own ambiguous "large viewport" instead of the real visible one, and worked around it by hand-measuring `--app-height` in JS and computing an explicit `top` in px for `#tabbar` (`positionTabbarForIOS()`) and `.sheet-panel` (`positionSheetForIOS()`), iOS-only. That workaround was never actually wrong — the round-24-followup debug numbers already confirmed it was computing exactly what it was told to. But it's fragile by construction: it depends on a resize/orientationchange/visualViewport-resize event firing to recompute, and standalone launch (no chrome to animate) doesn't reliably fire one after the very first paint — so if the very first `--app-height` reading is ever off, or the DOM order/timing of the very first `positionTabbarForIOS()` call doesn't land the way the rest of the chain assumes, nothing ever corrects it afterward. Two JS functions, one per element, also meant every *new* fixed bottom element would need its own copy of the same fix.

**The actual fix: stop fighting `position:fixed`'s containing-block ambiguity and sidestep it entirely.** `.screen` already had a reliable, working answer to "how tall is the real viewport" — the `--app-height` custom property, set from `visualViewport.height`/`innerHeight` (round 20-21) — it just wasn't shared with anything outside itself.
- `.sheet-backdrop`/`.sheet-panel`: these were already rendered as direct DOM children of `#screen` (`sheetHTML()`'s own comment: "a sibling of .view"), so `#screen` — `position:relative`, already sized via `height:var(--app-height,100dvh)` — was already sitting right there as a valid, correctly-sized containing block. Changed both from `position:fixed` to `position:absolute`; their existing `inset:0` / `bottom:0;height:50%` rules now resolve against `#screen` instead of the ambiguous large viewport. `positionSheetForIOS()` deleted outright — nothing left for it to do.
- `#tabbar`: this one is deliberately *not* inside `#screen` (`render()` wipes `#screen`'s innerHTML on every navigation, and `#tabbar` has to survive that), so it had no equivalent ready-made ancestor. Added one: `#uiLayer`, a new persistent sibling of `#screen` (same "survives render()" reasoning as `#refreshBtn`), sized with the exact same `height:var(--app-height,100dvh)` `.screen` uses, `pointer-events:none` so it doesn't intercept taps meant for `#screen` underneath (`#tabbar` turns pointer-events back on for itself). `#tabbar` moved inside it and switched from `position:fixed` to `position:absolute`. `positionTabbarForIOS()` deleted outright too.
- Also restored the plain 16px `.tabbar` `bottom` gap for every platform, not just non-iOS — round 24's iOS-only 8px value existed specifically to compensate for the large-viewport bug this round removes at the root, not as an independently-requested design value (round 23's actual ask was "exactly 16px", full stop). Flagged clearly in the CSS comment as easy to revert per-platform if 16px reads differently from what round 24 intended once actually seen on a device.
- `onViewportChange()` simplified to just `setAppHeight()` + `updateStackClearance()` — the only two things left that do anything. `isIOS` itself is kept (the diagnostics panel still reports it) even though nothing branches on it for layout any more.
- Debug panel extended: added `.screen rect` and `.ui-layer rect` readouts (should always match exactly — that's the thing to check first on a real device) and dropped the now-meaningless `tabbar inline top/bottom` line (nothing sets inline styles on it any more).

**Zoom disabled.** Added `maximum-scale=1, user-scalable=no` to the viewport meta tag. Documented the real caveat rather than pretending it's airtight: iOS Safari has, since iOS 10, deliberately still allowed pinch-zoom regardless of this flag as a WCAG 1.4.4 accessibility override — this reliably blocks it in the standalone/home-screen app (no Safari UI involved at all) and blocks double-tap-zoom everywhere, but a user could still pinch-zoom while it's open as an ordinary Safari tab. That's Apple's own intentional accessibility escape hatch, not a gap in this fix.

The real cause was `.screen{ height:100svh; }`. This was a deliberate choice from round 1 (see the CSS comment that was there) — `svh` ("small viewport height") locks to the viewport's height when a mobile browser's own chrome (Safari's address bar / bottom toolbar) is fully expanded, specifically so the layout wouldn't visibly resize/jump every time that chrome shows or hides on scroll. The trade-off nobody caught until now: once Safari's chrome actually auto-hides — which happens on essentially any scroll, i.e. constantly in normal use — the real visible viewport becomes taller than `100svh`, but `.screen` stays locked at the smaller size. The newly-revealed strip at the bottom isn't covered by `.screen` at all; it's just plain `<body>` showing through. Since `body{ background:var(--bg) }` is the exact same color as `.screen`'s own background, there's no visible seam — it just reads as "the app doesn't reach the bottom," which is exactly what was reported. Everything pinned to `.screen`'s bottom edge (`#tabbar`, `.intro-cta`, day-view padding) inherited the same offset from the window's true bottom.

Fix: swapped `100svh` for `100dvh` (dynamic viewport height), which tracks the browser's *current* real viewport continuously rather than locking to its smallest possible state. Updated the CSS comment to explain the trade-off and why `dvh` wins now: the "jump" `svh` was trying to prevent is, on current iOS/Android, a smooth live resize as the browser chrome animates in/out — not the jarring instant cut the original comment was guarding against.

**Real bug: the X close button stopped working the moment drag-to-dismiss shipped.** `wireSheetDrag()` puts a `pointerdown` listener directly on `.sheet-header` (one of its two always-draggable sources, alongside `.sheet-handle`), and that listener doesn't distinguish what was actually tapped inside the header — including the close button that lives in it. So the header ate the click that would have fired the button's own `data-sheet-close` handler, and the tap was silently reinterpreted as a zero-distance drag that just snapped back open. Fixed with one guard at the top of `onDown`: `if(e.target.closest('.sheet-close')) return;` — the close button is now explicitly excluded from starting a drag at all, so its own click fires normally. ## ROUND 8 — 2026-09-15
The deck shadow-clip bug from round 7 turned out to only be half-fixed, plus wider cards.

**The real fix for the shadow clip.**
The user sent a real-iPhone screenshot showing the front card's box-shadow still hard-cut at the bottom, right where round 7's fix was supposed to have addressed it. Round 7's `flex:1 1 auto` change on `.stack-wrap` was real and worth keeping — it does stop the page (`.view`) from ever needing to scroll when the hero's safe-area-dependent height grows — but it turned out to be treating a different symptom of the same underlying situation, not the actual clipping. The actual cause: `.stack-card` is absolutely positioned with `top:50%; height:100%` (plus a `translateY(-50%)`), which resolves those percentages against its *containing block* — and per spec, an absolutely-positioned element's containing block is its nearest positioned ancestor's **padding box**, not its content box. `.stack-wrap` has `padding: 2px 0 14px`, but because that padding is already included in the containing block the card sizes itself against, the card's own box always extends to stack-wrap's exact *outer* edge — the 14px of bottom padding creates no usable empty space below the card at all, contrary to what it looks like it should do. Since `.view` clips overflow (it's `overflow-y:auto; overflow-x:hidden`, which clips both axes per spec), and the card's shadow doesn't count toward scrollable content, the shadow got hard-cut the instant it crossed `.view`'s edge, with zero pixels of slack to work with.

Fixed by reserving genuine empty space *below* `.stack-wrap`'s own box instead of padding inside it: added `margin-bottom:48px`. Flexbox still correctly subtracts a flex item's margin when computing how much space `flex:1 1 auto` claims as "remaining," so `.view` still never needs to scroll — but now there's 48px of real gap between the bottom of the deck and the bottom of `.view` for the shadow (`0 22px 40px -18px rgba(0,0,0,.55)`, which bleeds roughly 44px below the card) to render into cleanly.

Verified with Playwright by measuring the actual gap between the front card's `getBoundingClientRect().bottom` and `.view`'s own `bottom` — confirmed 48px of real slack, at both a normal 390×844 viewport and a short 390×700 one, with `.view.scrollHeight === .view.clientHeight` (no scroll) holding at both sizes too.

**Wider cards.**
`width:min(300px, 82%)` → `width:min(320px, 82%)`. At most phone widths this mostly just raises the ceiling the 82%-of-viewport cap was already hitting, rather than adding a flat 20px everywhere.

**5. The round-4 "card pops to fullscreen" bug was still happening — because round 4's fix had a bug of its own.**
Root cause: round 4 added `cardEl.style.transition = 'none'` right before `openDayFlip()` snaps the card to its resting transform and measures it, specifically to make that snap instant/synchronous. That part worked. But the code never set `cardEl.style.transition` back afterward — and a few lines later, `cardEl.classList.add('opening')` adds a class that defines `transition: top .52s ..., left .52s ..., width .52s ...` etc. An inline `style.transition` always wins over a class-based transition rule, *regardless of which was applied more recently* — so that leftover `transition:none` silently cancelled the entire box-morph grow-to-fullscreen animation for the rest of the function. Verified by sampling the opening card's `getBoundingClientRect()` every 50ms after a tap: size now grows gradually frame over frame (e.g. 300×677 → 685 → 719 → 774 → ... → 840) instead of jumping straight to the fullscreen size on the first frame — checked for both a plain tap and the swipe-then-immediately-tap sequence from round 4, to confirm both fixes still work together correctly.

## ROUND 1 — 2026-09-15
Built the Explorer Mode prototype end to end and set up version control for the project.

**Built:**
- Home screen "reel": a draggable 10-day card stack with pointer-based drag physics (commit distance/velocity thresholds), natural per-card resting tilt (a small deterministic jitter array, not random-per-render so it stays stable across re-renders).
- Open animation: tapping the front card flips it in place via a combined 3D CSS flip (`rotateY`) and a FLIP-technique box-morph (animating `top/left/width/height/border-radius` with a captured "from" rect), so the card grows to fill the screen without any scale-based distortion of its photo or text. The rest of the deck gathers into a tidy, square, untilted pile at the same time, with box-shadows fading out fast so overlapping shadows don't smear into a blob.
- Close animation: the true reverse — unflip while shrinking back into the exact deck slot the card came from (using a cached target rect from the original open, derived from the card's rotation-invariant center point + its own unrotated layout size, not a naive `getBoundingClientRect()` which is inflated by rotation). The deck spreads back out to its natural fan timed to finish as the card lands.
- Day 1 and Day 2 ("Lost in Translation") full detail screens: weather-informed prep card (energy/walking/outdoor/dress/bring/first-move), progressive chapter reveal (hidden → on the way → revealed) with a manual "We're here" location-check trigger, expandable "About this place" per chapter, and a spoiler-free "Tomorrow" wake-up/leave teaser.
- Locked-day treatment: grayscale + blur + darkened hero, hidden title, visible date + teaser.
- Day 2's card given a real photo. The user first shared an AI-stylized "Lost in Translation" movie poster (real actors, real film branding) — declined per policy, since it depicted real named public figures. User uploaded their own neon Tokyo alley photo instead, embedded as base64 JPEG.
- PWA installability: `manifest.json`, a generated `icon-512.png`, and the `<link rel="manifest">` / apple-mobile-web-app meta tags needed to "Add to Home Screen" and launch full-screen.
- Stripped the outer demo/gallery presentation (title+description header, decorative film-strip dots, phone-bezel mockup) once the page could be installed as a real app — it now fills the browser edge to edge instead of simulating a phone.

**Bugs found and fixed (via Playwright screenshots + frame-by-frame screen-recording analysis):**
1. *Locked-card corner radius not clipping.* Root cause: a Chromium quirk where `overflow:hidden` + `border-radius` fails to clip a `filter`-bearing descendant (the grayscale/blur) when nested inside a `preserve-3d` ancestor (the flip container). Fixed with `clip-path: inset(0 round 22px)` on `.hero`, which is a compositor-level clip unaffected by the bug.
2. *Shadow "smear" during the gather animation.* Multiple stacked cards' shadows piling up read as a detached blob. First fix attempt (differentiated shadow strength by front/back card) was explicitly rejected by the user — it made background cards disappear. Correct fix: fade `box-shadow` alone (not opacity, not the whole card) out fast when gathering and back in once spread out and landed.
3. *"IN PROGRESS" pill flashing to its real color right at the end of closing.* The transient element built by hand in `closeDayFlip()` for the closing card never got the `active` status class that `homeScreen()` gives real deck cards, so the pill's colored background was missing for the whole animation and only appeared the instant the final DOM swap happened — reading as a jump. Fixed by matching every class `homeScreen()` would have given the card, not just `locked`.
4. *Deck-spread race condition.* The final DOM swap ran on a flat `setTimeout(820ms)` that assumed the deck's separately-scheduled `.48s` spread-out transition (started at the 300ms mark, nominally finishing at 780ms) would always be done — a ~40ms margin between two independently-scheduled timers. Under real jank (confirmed: a running screen recorder was enough) the swap could fire before the deck actually finished sliding into its resting fan, snapping it to its final position mid-motion. Fixed by waiting on the real `transitionend` event (with a generous fallback timer only as a safety net) instead of a guessed delay.
5. *Subpixel "shimmer" across the whole card at the very end of closing.* This is the one that took the most digging — a user-submitted screen recording, frame-by-frame diffed, showed literally every edge on the card (photo edges, text, pill outline) shifting at once, well after the animation had visually stopped. Root cause: `closeDayFlip()` landed the card correctly, then called the generic `render()`, which destroys every element in `#screen` and rebuilds fresh ones from `homeScreen()`. Even though the new element lands at an identical pixel rect (verified to sub-pixel accuracy), it's a brand-new, freshly-laid-out element replacing one the browser had been continuously animating/compositing on its own GPU layer — and that swap makes the browser re-rasterize text/photo edges at a very slightly different subpixel offset, a one-frame visual "pop." Fixed by folding the same DOM element (the just-landed card) directly into the deck as its permanent front card instead of discarding and recreating it: strip the animation-only inline styles, add it to `#stackwrap`, promote the background decoy layer to being the real view, and re-wire event handlers — no element is ever swapped at the moment the animation ends.
6. *Non-bug, ruled out:* after fix #5, the user still reported an "offset movement" and sent a fresh screen recording. Diffing it initially looked like the same shimmer, until it turned out the video was recorded through the claude.ai chat's in-app preview running in Safari — the user separately confirmed the exact same build has no issue at all in real Chrome, and none in standalone Safari either. Concluded: a rendering quirk specific to that one embedded webview context, not a real bug. Worth remembering so it isn't re-investigated from scratch if it resurfaces.

- Diagnosed animation timing bugs primarily via Playwright (`/opt/pw-browsers/chromium`), using in-page `performance.now()`-based sampling rather than trusting Python-side `wait_for_timeout` loops (which accumulate IPC overhead and skew nominal vs. real elapsed time), plus artificial CPU throttling (`Emulation.setCPUThrottlingRate`) to simulate the jank a real screen recorder introduces.
