## ROUND 6 — 2026-09-15
Small follow-up to round 5: swapped in transparent-background versions of the hero mark artwork.

- The user pointed out the opaque round-5 mark images (a white square for light mode, a black square for dark mode) sat in a faintly visible square against the page background rather than blending in. They supplied new versions of both — same circle-plus-vertical-text design, same light/dark split (black text for light mode, white text for dark mode) — but with a transparent background instead of a solid fill.
- Swapped the `MARK_LIGHT`/`MARK_DARK` base64 constants in `index.html` for the new images; no other markup or theme-switching logic needed to change since it was already keyed off the same light/dark pairing.
- `.home-hero .mark img`'s `border-radius:22%; object-fit:cover` was dropped in favor of plain `object-fit:contain` — the border-radius existed only to round off the opaque square's corners, which no longer exist now that the background is transparent; `contain` (over `cover`) avoids any risk of clipping the artwork's off-center content now that there's no uniform background to crop into.
- `icon-512.png` (the installed-app icon / `apple-touch-icon`) deliberately was NOT swapped to the new transparent artwork — kept the round-5 opaque light version. Installed home-screen icons don't handle real transparency reliably across platforms (iOS in particular backfills transparent regions with an unpredictable color), so an opaque icon stays the safer choice there even though the in-page hero mark benefits from transparency.
- Verified with Playwright screenshots in both light and dark mode — the mark now reads as floating directly on the page in both themes, no visible edge.

## ROUND 5 — 2026-09-15
User's own icon artwork replaces the placeholder circle mark, plus a spacing/safe-area pass on the home hero.

**Icon artwork:**
- Replaced the plain CSS red circle used as the home hero's mark with two PNGs the user supplied: a light-bg variant (white background, red circle, black vertical "スローリー ニホン" text) and a dark-bg variant (black background, same circle, white text), both 512×512. Embedded both as base64 `data:` URIs in `index.html` (`MARK_LIGHT`/`MARK_DARK` constants, next to `heroStyle()`), rendered as two `<img>` elements in `.home-hero .mark`, and toggled with the same `prefers-color-scheme`/`data-theme` CSS pattern already used for every other themed value in the file — so it follows system/manual theme exactly like everything else.
- Replaced `icon-512.png` on disk with the light variant (used by `manifest.json`'s two icon entries and the `<link rel="apple-touch-icon">` tag). Picked light over dark because it matches `manifest.json`'s `background_color` (`#fafafa`), which is what shows through as the PWA splash background while the icon is still loading — a static manifest icon can't theme-swap the way the in-page mark can, so one variant had to be chosen.
- Flagged, not fixed: the artwork's vertical text sits close to the right edge of the 512×512 canvas, and `manifest.json` lists a `maskable` purpose entry for this icon — OS home screens crop maskable icons to roughly their inner ~80% "safe zone," which could clip that text on an aggressive (e.g. circular) mask shape. Didn't redesign the user's artwork to pull the text inward without being asked; noted in PROJECT-CONTEXT.txt's Known Gaps for them to check once actually installed on a device.

**Home-screen spacing:**
- Hero top padding changed from a flat `44px` to `calc(env(safe-area-inset-top, 0px) + 24px)`, so it clears the iPhone notch/Dynamic Island (or any other device inset) instead of guessing a value generous enough to hopefully clear every device — collapses to a plain 24px with no visual change on a device/browser with no inset at all (desktop, older phones).
- Gap from the hero's content down to the top of the card stack set to a flat 48px: `.home-hero`'s bottom padding dropped to 0 and `.stack-wrap`'s `margin-top` changed from `6px` to `48px`, so the spacing is owned by exactly one rule instead of two paddings silently adding together. Verified with a Playwright DOM measurement (`card.getBoundingClientRect().top - hero.getBoundingClientRect().bottom === 48`), not eyeballed from a screenshot.

## ROUND 4 — 2026-09-15
Design cleanup pass on type scale and spacing, a home-screen/card redesign, and a real animation bug fix.

**Type scale (min. 14px):**
- Defined a fixed 3-tier scale and applied it across the whole stylesheet: **16px regular** for long-form readable copy (chapter blurbs, "about this place" paragraphs, teasers directly under a heading, tomorrow/locked-day notes), **14px small** for secondary/meta/button text (dates under headings, prep values, weather temp/condition, buttons, confirm-row text), and **12px bold uppercase** for small labels (chapter tags, prep-cell labels, section labels like "CHAPTERS"/"TOMORROW", the card's bottom date line, hourly-forecast time ticks). Previously sizes were scattered from 8.5px up to 15.5px with no consistent logic. Big headings (20–25px day titles) were left untouched — they were already well above the floor.
- A few paddings were nudged up alongside the larger text so nothing reads as cramped: the status pill, `.ctag`, `.resetbtn`, `herebtn`, and the "about" panel's max-height.
- Verified via Playwright screenshots that nothing wraps/overflows at the new sizes in the tightest spots: the 6-column hourly-forecast grid and the 3-column prep-info grid.

**Spacing:**
- Standardized every page-level horizontal margin/padding (`.dayhead`, `.backhero-text`, `.lockednote`, `.prep`, `.chapters`, `.tomorrow`, `.journalflag`, `.lastupdate`, the home hero) to a single 24px, replacing an inconsistent mix of 16/17/20px. Left the stack-card's own internal 17px photo-caption padding alone — that's inset from the *card's* edge, a different concept from the page's device-edge margin.

**Home screen:**
- Replaced the old left-aligned "wordmark + date range" header with a centered hero: a red circle mark, "Japan Slowly" beneath it, then the trip date range beneath that.
- Removed the demo-preview description line ("Preview state: evening of Day 2, shown mid-experience for this demo...") entirely, not just hidden.

**Deck cards:**
- Status pill now only renders for locked cards ("Locked"); unlocked (journal / in-progress) cards no longer show any status label at all. The `.active`-specific pill color override was removed since nothing uses it anymore.
- Removed the top-right "#02 / 10" frame-number badge. That trip-position info now prefixes the bottom date line instead: "Day 2 / 10 · SAT 26 SEP".

**Bug fixed:**
1. *Card visibly "pops" to full size right as the open animation starts — but only if you swipe to focus a card and then tap it immediately, not if you close and reopen.* Root cause: `openDayFlip()` captures a "from" rect for the box-morph using the card's rotation-invariant center point paired with its own *unrotated, unscaled* layout size (`offsetWidth`/`offsetHeight`, which `transform` never affects) — a deliberate round-1 fix for a different problem (rotation inflating `getBoundingClientRect()`). That assumes the card is already sitting at its settled resting transform (`scale(1) rotate(0)`) when opened. But `endDrag()` promotes a new front card by updating `state.stackIndex` and calling `applyStack()`, which kicks off the ordinary `.6s` spring transition that grows/un-tilts that card from whatever smaller, jittered transform it had as a background card — and a tap right after the swipe (part of the same gesture) can land well before that transition finishes. In that window the card's actual on-screen size was still mid-transition (smaller/tilted), but the "from" box was built from its full resting size regardless — so setting that size directly (bypassing the transition) made it visibly snap to full size for one frame before the flip-grow animation took over. Fixed by having `openDayFlip()` synchronously force the card to its resting transform (`transition:none` + `stackTransform(stackStyle(0, idx))`, with a forced reflow) *before* any measuring happens, so the measured box always matches what's actually on screen. Verified by scripting the exact repro in Playwright (swipe, then click with zero wait) and sampling the opening element's `getBoundingClientRect()` every 60ms — the first frame now reports the card's correct resting size (300×557) instead of a smaller mid-transition one.

## ROUND 1 — 2026-09-15
Built the Explorer Mode prototype end to end and set up version control for the project.

**Built:**
- Home screen "reel": a draggable 10-day card stack with pointer-based drag physics (commit distance/velocity thresholds), natural per-card resting tilt (a small deterministic jitter array, not random-per-render so it stays stable across re-renders).
- Open animation: tapping the front card flips it in place via a combined 3D CSS flip (`rotateY`) and a FLIP-technique box-morph (animating `top/left/width/height/border-radius` with a captured "from" rect), so the card grows to fill the screen without any scale-based distortion of its photo or text. The rest of the deck gathers into a tidy, square, untilted pile at the same time, with box-shadows fading out fast so overlapping shadows don't smear into a blob.
- Close animation: the true reverse — unflip while shrinking back into the exact deck slot the card came from (using a cached target rect from the original open, derived from the card's rotation-invariant center point + its own unrotated layout size, not a naive `getBoundingClientRect()` which is inflated by rotation). The deck spreads back out to its natural fan timed to finish as the card lands.
- Day 1 and Day 2 ("Lost in Translation") full detail screens: weather-informed prep card (energy/walking/outdoor/dress/bring/first-move), progressive chapter reveal (hidden → on the way → revealed) with a manual "We're here" location-check trigger, expandable "About this place" per chapter, and a spoiler-free "Tomorrow" wake-up/leave teaser.
- Locked-day treatment: grayscale + blur + darkened hero, hidden title, visible date + teaser.
- Day 2's card given a real photo. The user first shared an AI-stylized "Lost in Translation" movie poster (real actors, real film branding) — declined per policy, since it depicted real named public figures. User uploaded their own neon Tokyo alley photo instead, embedded as base64 JPEG.
- PWA installability: `manifest.json`, a generated `icon-512.png`, and the `<link rel="manifest">` / apple-mobile-web-app meta tags needed to "Add to Home Screen" and launch full-screen.
- Stripped the outer demo/gallery presentation (title+description header, decorative film-strip dots, phone-bezel mockup) once the page could be installed as a real app — it now fills the browser edge to edge instead of simulating a phone.

**Bugs found and fixed (via Playwright screenshots + frame-by-frame screen-recording analysis):**
1. *Locked-card corner radius not clipping.* Root cause: a Chromium quirk where `overflow:hidden` + `border-radius` fails to clip a `filter`-bearing descendant (the grayscale/blur) when nested inside a `preserve-3d` ancestor (the flip container). Fixed with `clip-path: inset(0 round 22px)` on `.hero`, which is a compositor-level clip unaffected by the bug.
2. *Shadow "smear" during the gather animation.* Multiple stacked cards' shadows piling up read as a detached blob. First fix attempt (differentiated shadow strength by front/back card) was explicitly rejected by the user — it made background cards disappear. Correct fix: fade `box-shadow` alone (not opacity, not the whole card) out fast when gathering and back in once spread out and landed.
3. *"IN PROGRESS" pill flashing to its real color right at the end of closing.* The transient element built by hand in `closeDayFlip()` for the closing card never got the `active` status class that `homeScreen()` gives real deck cards, so the pill's colored background was missing for the whole animation and only appeared the instant the final DOM swap happened — reading as a jump. Fixed by matching every class `homeScreen()` would have given the card, not just `locked`.
4. *Deck-spread race condition.* The final DOM swap ran on a flat `setTimeout(820ms)` that assumed the deck's separately-scheduled `.48s` spread-out transition (started at the 300ms mark, nominally finishing at 780ms) would always be done — a ~40ms margin between two independently-scheduled timers. Under real jank (confirmed: a running screen recorder was enough) the swap could fire before the deck actually finished sliding into its resting fan, snapping it to its final position mid-motion. Fixed by waiting on the real `transitionend` event (with a generous fallback timer only as a safety net) instead of a guessed delay.
5. *Subpixel "shimmer" across the whole card at the very end of closing.* This is the one that took the most digging — a user-submitted screen recording, frame-by-frame diffed, showed literally every edge on the card (photo edges, text, pill outline) shifting at once, well after the animation had visually stopped. Root cause: `closeDayFlip()` landed the card correctly, then called the generic `render()`, which destroys every element in `#screen` and rebuilds fresh ones from `homeScreen()`. Even though the new element lands at an identical pixel rect (verified to sub-pixel accuracy), it's a brand-new, freshly-laid-out element replacing one the browser had been continuously animating/compositing on its own GPU layer — and that swap makes the browser re-rasterize text/photo edges at a very slightly different subpixel offset, a one-frame visual "pop." Fixed by folding the same DOM element (the just-landed card) directly into the deck as its permanent front card instead of discarding and recreating it: strip the animation-only inline styles, add it to `#stackwrap`, promote the background decoy layer to being the real view, and re-wire event handlers — no element is ever swapped at the moment the animation ends.
6. *Non-bug, ruled out:* after fix #5, the user still reported an "offset movement" and sent a fresh screen recording. Diffing it initially looked like the same shimmer, until it turned out the video was recorded through the claude.ai chat's in-app preview running in Safari — the user separately confirmed the exact same build has no issue at all in real Chrome, and none in standalone Safari either. Concluded: a rendering quirk specific to that one embedded webview context, not a real bug. Worth remembering so it isn't re-investigated from scratch if it resurfaces.

**Process / workflow:**
- Diagnosed animation timing bugs primarily via Playwright (`/opt/pw-browsers/chromium`), using in-page `performance.now()`-based sampling rather than trusting Python-side `wait_for_timeout` loops (which accumulate IPC overhead and skew nominal vs. real elapsed time), plus artificial CPU throttling (`Emulation.setCPUThrottlingRate`) to simulate the jank a real screen recorder introduces.
- Diagnosed the two most stubborn visual bugs by asking the user for a screen recording, extracting frames with `ffmpeg`, and diffing consecutive frames pixel-by-pixel (cropped to the app's own region, since the user's desktop recordings included other windows/a dock that otherwise polluted the diff) to find the exact frame where something changed unexpectedly.
- Created the `github.com/everydayou/japan-slowly` repo (already existed, empty) as the project's source of truth. This session's cloud sandbox has no GitHub credentials of its own, so files were written directly onto the user's Mac (via a connected-folder bridge) and committed there; the user pushed manually from their own authenticated terminal.
- Adopted the PROJECT-CONTEXT.txt / CHANGELOG.txt split used on the user's other project ("leve"): a short, current-state-only snapshot meant to be read at the start of every chat, plus a full append-only round-by-round log kept separately so the snapshot never bloats.
