## Design & Interaction Contract — fixed rules (read BEFORE touching UI/animation)
These were each arrived at after multiple rounds of iteration and user feedback. Don't change them without being explicitly asked to revisit them:
- **Type scale is 16px regular / 14px small / 12px bold uppercase for labels — nothing smaller than 14px except that third label tier** (round 4). Big headings (day titles, 20–25px) are unaffected. Rule of thumb: long-form readable copy (chapter blurbs, "about" text, teasers directly under a heading, tomorrow/locked-day notes) is 16px; secondary/meta/button text (dates under headings, prep values, buttons, confirm rows) is 14px; small all-caps eyebrows, tags and pills (chapter tags, prep-cell labels, "chapters"/"tomorrow" section labels, the card's bottom date line, hourly-forecast time ticks) are 12px + `font-weight:700` + uppercase. Don't reintroduce anything under 14px outside that labeled third tier.
- **Side margins between content and the device edge are 24px everywhere** (round 4) — the page-level horizontal padding/margin on `.dayhead`, `.backhero-text`, `.lockednote`, `.prep`, `.chapters`, `.tomorrow`, `.journalflag`, `.lastupdate` and the home hero was standardized from a mix of 16/17/20px to a single 24px. The stack-card's own internal photo-caption padding (17px, inset from the *card's* edge, not the device's) is a separate, unrelated value and was left alone.
- **The home screen's top hero is a centered red circle mark + "Japan Slowly" wordmark + trip date range** (round 4), replacing the old left-aligned wordmark-only header — and the demo-preview description line beneath it ("Preview state: evening of Day 2...") was removed entirely, not just hidden. `.home-hero` in index.html.
- **Deck cards only show a status pill when locked** (round 4) — journal/"in progress" (unlocked) cards no longer carry any status label. The trip-position indicator ("Day 2/10") that used to sit in a top-right badge now lives after the bottom date instead — **date/day-of-week first, then the count** ("SAT 26 SEP · Day 2/10", reordered round 7 from an earlier "Day 2 / 10 · SAT 26 SEP"); there is no separate top-right badge anymore.
- **The home hero mark is the user's own icon artwork, not a plain CSS circle** (round 5, updated round 6) — two PNGs (`MARK_LIGHT`/`MARK_DARK`, embedded as base64 in `index.html`), swapped with the same `prefers-color-scheme`/`data-theme` pattern the rest of the token system uses. Round 6 replaced both with transparent-background versions the user supplied (black text for light mode, white text for dark mode) — the mark now blends directly into the page instead of sitting in a visible opaque square, which is why `.home-hero .mark img` no longer has a `border-radius`/`object-fit:cover` clip (nothing to trim once there's no background fill). `icon-512.png` (the installed-app icon / `apple-touch-icon`) intentionally still uses the round-5 **opaque** light variant, not this transparent one — installed home-screen icons render badly with real transparency (iOS in particular fills transparent areas with an unpredictable backdrop), and a static manifest icon can't theme-swap the way the in-page mark does anyway. Don't regenerate/replace either without keeping both a light and dark variant supplied, and don't swap the transparent artwork into `icon-512.png`.
- **Home-hero vertical spacing is deliberate, not arbitrary** (round 5, tightened round 7): the hero's top padding is `calc(env(safe-area-inset-top, 0px) + 24px)` — not a flat pixel value — specifically so it clears the iPhone notch/Dynamic Island (which round 3 already learned only ever shows up on a real device). Round 7 replaced the hero's uniform flex `gap` with specific per-pair margins: mark→wordmark 4px, wordmark→range 2px. The hero's own bottom padding is 0; the gap down to the top of the card stack (40px as of round 7, was 48px in round 5) is owned entirely by `.stack-wrap`'s `margin-top` instead, so the two don't stack into something bigger than intended. Don't add padding to `.home-hero`'s bottom edge without correspondingly shrinking `.stack-wrap`'s margin-top.
- **`.dayhead` (the day-detail header, holding the back button) also needs `env(safe-area-inset-top)`** (round 7) — without it, the back button sat directly under the iPhone status bar/clock, sometimes fully unreachable under it. Same pattern as the home hero and `.refresh-fab`.
- **`.stack-wrap` sizes itself with `flex:1 1 auto`, not a fixed percentage** (round 7, was `flex:0 0 66%` since round 1) — a fixed percentage of the deck plus the hero's own (now variable, safe-area-dependent) height could together exceed the screen height on a real device/shorter viewport, forcing `.view` to scroll. Don't revert to a fixed flex-basis without re-testing on a short viewport with a large safe-area-inset-top.
- **`.stack-wrap` also carries `margin-bottom:48px`, reserved space for the front card's box-shadow to bleed into** (round 8) — this is a *separate* fix from the `flex:1 1 auto` change above, for a different symptom. Even with no page-level scroll, the shadow was still getting hard-clipped at `.view`'s bottom edge, because a `.stack-card`'s `top:50%/height:100%` positioning is relative to its containing block, which for an absolutely-positioned element **includes its parent's padding** — so `.stack-wrap`'s own `padding-bottom` creates zero usable slack below the card; the card's box always extends to stack-wrap's exact outer edge regardless of that padding value. The only way to give the shadow real room is genuine empty space *below* stack-wrap's own box, which is what this margin reserves. flexbox still correctly subtracts a flex item's margins from what `flex:1 1 auto` treats as "remaining space," so the page still never needs to scroll. 48px comfortably covers the shadow's `0 22px 40px -18px` spec (~44px of visible bleed). If the shadow's offset/blur/spread values ever change, re-check whether 48px is still enough headroom — don't assume it scales automatically.
- **Deck cards are `width:min(320px, 82%)`, not a flat 300px** (round 8) — widened 20px on request. At most viewport widths this hits the 82% cap rather than the 320px ceiling, so the practical effect is similar to raising the old 300px cap, not a fixed +20px on every device.
- **Opening a card synchronously snaps it to its resting front-card transform (`scale(1) rotate(0)`) before measuring its "from" rect, AND that snap's `transition:none` must be cleared back to `''` immediately after** (round 4, regression fixed round 7, `openDayFlip` in index.html). The snap-before-measure fixes a real bug where tapping the newly-focused card immediately after a swipe (before its .6s snap-into-focus transition finished) measured it mid-transition but then sized the "from" box using its resting (unrotated, unscaled) layout size, so it visibly popped to full size right as the open animation began. Closing-then-reopening never showed this because the card was always already settled by then. Don't remove this snap-before-measure step without retesting the swipe-then-immediately-tap case specifically — a delayed tap after the swipe settles won't reproduce it. **But** leaving that snap's `cardEl.style.transition = 'none'` in place afterward is a *different*, worse bug: an inline `style.transition` always out-ranks a class-based transition rule regardless of add order, so it silently cancelled the `.opening` class's own top/left/width/height transition for the rest of the function — every open looked like an instant jump to fullscreen size with only the flip's rotateY still animating. Round 7 added `cardEl.style.transition = '';` right after the forced-reflow flush to clear it. If this class of bug resurfaces, check every place that sets `el.style.transition` directly for a matching reset later in the same flow.
- **The home-reel drag zone needs `touch-action:none` on `.stack-wrap`, and `html`/`body` need to be locked from ever scrolling/bouncing** (round 3): a real phone was the only way this surfaced — desktop mouse/trackpad testing never showed it. With `touch-action:pan-y` (the original value) a real finger drag is never perfectly horizontal, so the browser's own vertical-pan gesture kept hijacking the custom drag as a native scroll/bounce, fighting the JS handler. Separately, `html`/`body` had no `overflow`/`overscroll-behavior` rules at all, so the whole document itself could pan and rubber-band in both directions even though `.screen` internally has `overflow:hidden`. Fixed with `touch-action:none` on `.stack-wrap`, `html,body{overflow:hidden;overscroll-behavior:none}` + `body{position:fixed;inset:0}`, and `overscroll-behavior:contain` on `.view` (the one element that's *supposed* to scroll, for a day's detail content). Don't reintroduce `pan-y` or drop the html/body lock without testing drag on an actual phone afterward — this class of bug doesn't show up any other way.
- **Design tokens are ported from the `leve` project's design system** (round 2): the `:root` block in `index.html` uses the same semantic roles leve uses (surface/content/border/accent, light+dark remap via `prefers-color-scheme` and a `data-theme` override) and the same Outfit typeface everywhere, replacing the original Fraunces/Work Sans/IBM Plex Mono mix. The one deliberate divergence: **the accent hue is a torii-red (`#d6432e` light / `#ff7a61` dark), not leve's mint** — chosen specifically to keep a Japan-flavored identity instead of reading as a re-skinned iOS app. Variable *names* (`--bg`, `--ink`, `--accent`, etc.) were kept unchanged from the pre-round-2 file so no other rule needed touching. Don't silently revert to the old warm/paper palette or reintroduce the three-font mix without being asked.
- **Card jitter range is 1–3°**, applied only to non-front deck cards (`CARD_JITTER` array in index.html). A wider 3–5° range was tried and explicitly rejected as "too much."
- **The front/focused card has NO tilt** (`rot:0` at offset 0). Adding one was tried, then explicitly reverted — it interacted badly with the deck-movement animation. Don't re-add without the user raising it again.
- **Open/close uses a combined 3D flip + FLIP-technique box-morph** (animating top/left/width/height, not `transform:scale`), specifically so photo/text proportions never distort. This is why the code reparents the card into `#screen` and manually computes pixel rects instead of using simpler CSS.
- **The rest of the deck gathers into a tidy, square, untilted stack while one card is open/closing**, then spreads back into its natural fan as the card lands. This exists specifically to mask the fact that a rotated card can't gracefully unrotate into a tilted slot on its own — it's a workaround, not a feature in its own right.
- **Card shadows fade via `box-shadow` transition only, never via opacity** — fading the whole card was tried and rejected ("makes the cards behind disappear").
- **The drag-release snap uses a gentle spring/overshoot curve** (`cubic-bezier(.34,1.56,.64,1)`, .6s — round 3), not a plain ease-out. The original curve decelerated almost immediately, so nearly all the motion happened in the first sliver of the transition and read as an abrupt snap regardless of duration; the spring curve settles slightly past rest before easing back, which reads as a natural physical "landing." This is specifically for the drag-to-browse release on the home reel — NOT the day open/close flip below, which is a separate, independently-tuned animation.
- **On close, the animated card element is folded directly into the deck as the permanent front card, not destroyed and rebuilt via a full `render()`.** This was a real bug (a one-frame subpixel "shimmer" from swapping a continuously-animated element for a freshly-laid-out one) — don't reintroduce a full-rebuild-on-close pattern.
- **The outer "gallery" demo chrome (title/description header, decorative side dots, phone-bezel mockup) has been removed.** The page is meant to be opened directly / installed as a home-screen app, so it should always just BE the app, full-bleed — don't reintroduce a phone-simulation wrapper.
- **A "jump" that looked like a real animation bug turned out to be a Safari-in-webview rendering quirk specific to the claude.ai chat's in-app preview** — confirmed fine in real Chrome and standalone Safari. If something like this comes up again, reproduce it in an actual browser (not the chat preview) before spending time on it. (Round 3 reinforces this: several real bugs — the touch-action conflict, the missing viewport tag — likewise only ever showed up on an actual phone, never in desktop testing. Always verify anything drag/touch/scroll-related on a real device before concluding it's fine.)
- **No real, named public figures or copyrighted film/show branding in any generated imagery** (a stylized "Lost in Translation" poster with Bill Murray/Scarlett Johansson was declined for Day 2; the user's own uploaded photo was used instead).
- **App opens on a full-screen intro/splash view (`state.screen==='intro'`), not directly into the home carousel** (round 9) — mark, "Japan, unscripted" title, date range, and a "Start your journey" CTA (`.intro-cta`), sharing the same `heroMarkupHTML()` markup as the compact home hero so the two states can FLIP-morph between each other cleanly. Tapping the CTA calls `goHome()`: a FLIP transform on `.mark` (`markMorph`) from its large intro size/position to its small home position, while the wordmark/date/CTA cross-fade out and the deck cross-fades in underneath. Tapping the home view's hero (`.home-hero`, wired in `wireHome()`) calls `goIntro()`, which reverses the same FLIP. Don't naively CSS-`transform:scale()` the whole hero block for this — the intro title wraps to two lines and the home title is one line, so a scale-morph of the full block would visibly reflow/distort text; only the visually-identical `.mark` icon is FLIP-morphed, everything else cross-fades.
- **Icon references carry a cache-busting `?v=N` query string** (`manifest.json`'s two icon entries and the `<link rel="apple-touch-icon">` in `index.html`, currently `?v=9`) — round 9 fix for the app icon silently not updating. Browsers/OS cache an installed PWA icon very aggressively by exact URL, and `icon-512.png` had been swapped twice before (rounds 5 and 6) with the filename unchanged, so nothing ever told the OS a new copy existed. Bump this query param any time `icon-512.png`'s actual pixel content changes again. This only fixes it going forward for a *fresh* fetch/install — an icon already on a phone's home screen was cached at install time and needs a manual remove-and-re-add of the app to pick up a new one; there's no way to force that remotely.
- **The deck card animating INTO focus gets its own, slower, separate transition from the rest of the deck** (`applyStack()`, round 9) — `transform .85s cubic-bezier(.22,1,.36,1)` set as an inline style only on the card becoming the new front card, cleared back to `''` on that transition's `transitionend` so it doesn't linger and affect some later unrelated transform change on the same element (this is exactly the shape of bug the round-4/7 `transition:none` regression was — see that contract entry below — so the cleanup here is deliberate, not optional). The incoming card travels a much bigger transform delta (small tilted background card → full-size untilted front card) than the outgoing card does, which made it read as noticeably snappier even though both nominally shared the same `.6s` deck transition. Don't remove the inline-transition cleanup, and don't unify this back with the deck's shared timing without the user asking.
- **Accent red is `#E11401`** (round 9, was `#d6432e` from round 2) — light/dark hover variants (`--accent-soft`) and the dark-mode pair were re-derived proportionally (same HSL lightness/saturation offset from base as the old palette), not just eyeballed. - **A stay's Hotel row and its area content are rendered as two separate calls, never concatenated into one `aboutItemsHTML()` array** (round 19 follow-up, real bug fix) — `aboutItemsHTML(rows, chId)` decides flat-vs-grouped shape by inspecting ONLY `rows[0]`; the first version of `stayAboutHTML()` built `['Hotel', hotelValue].concat(areaRows)`, so when `areaRows` was the grouped shape (Stays 2/3, which have several named sub-places), the leading flat Hotel row made the whole array misdetect as flat and crash trying to read `row[0]`/`row[1]` off group objects. Fixed by rendering the Hotel row directly via `aboutRowHTML(['Hotel', hotelValue])` and passing `areaRows` to its own, separate `aboutItemsHTML()` call — both output plain `.about-item`/`.about-group` DOM nodes as siblings inside the same flex `.sheet-body`, so visually nothing changes, but the shape-detection bug is gone. If a stay's content ever needs a third block, keep it a separate call too rather than merging arrays.
- **`#tabbar`'s `[hidden]`/`.on` state must be kept in sync wherever `#refreshBtn`'s is — the two share the exact same persistent-sibling bug class** (round 19 follow-up, real bug fix) — `closeDayFlip()`'s `finishClose()` deliberately returns to home without calling `render()` (round 1's shimmer-avoidance fix), and had already been patched once (round 17) to manually set `refreshBtn.hidden=false` there since `render()` is the only other place that un-hides it. When `#tabbar` was added this round it wasn't given the same treatment, so it silently stayed hidden forever after the very first day-detail visit — identical symptom, identical root cause, identical fix (`finishClose()` now also sets `tabbar.hidden=false` and resets its `.on` classes). **Any future persistent sibling of `#screen` that `render()` toggles visibility for needs this same manual mirror inside `finishClose()`**, or it will hit this exact bug the moment someone opens and closes a day.

## What We're Building

- **Progress persistence is deliberately narrow — only `saveProgress()`/`loadProgress()`'s own explicit fields, never the whole `state` object** (round 21) — Day 2 chapters' `id`+`state` (hidden/revealed/ontheway), plus `screen`/`openDay`/`stackIndex`. - **`--stack-clearance` (round 21) is measured from `#tabbar`'s actual rendered position, not recalculated from its CSS formula** — deliberately, so it can't silently drift out of sync if `#tabbar`'s own size/offset/safe-area math ever changes independently. `updateStackClearance()` is the only place that writes it; don't hardcode a second margin value on `.stack-wrap` that could fight with it.
- **`setAppHeight()` / `positionTabbarForIOS()` / `updateStackClearance()` must always run in that exact order, via `onViewportChange()`** (round 22) — each depends on the one before it: `positionTabbarForIOS()` needs a current `--app-height`, and `updateStackClearance()` measures `#tabbar`'s resulting live position, so it needs `#tabbar` already in its final place. Don't register any of these three individually as a `resize`/`orientationchange`/`visualViewport resize` listener — always go through `onViewportChange()`, and if a fourth viewport-dependent function is ever added, add it to that same function in the correct dependency position rather than as its own separate listener.
- **`#tabbar`'s positioning is iOS-only special-cased (round 22)** — everywhere else it's plain CSS (`position:fixed; bottom:calc(env(safe-area-inset-bottom,0px)+16px)`, 16px as of round 23), confirmed correct by the user on Android/desktop. `positionTabbarForIOS()` (gated by `isIOS`, a `navigator.platform` sniff) overrides that with an inline `top`/`bottom:auto` only when `isIOS` is true; never applies this repositioning globally, and never remove the plain CSS `bottom` rule (it's still what non-iOS platforms use unmodified, and it's `#tabbar`'s own fallback position before the JS runs on iOS too). **As of round 24's follow-up, iOS's own JS-computed gap is deliberately 8px, not the shared CSS's 16px** — real on-device diagnostic data confirmed the positioning formula itself was already correct, but that standalone mode's mandatory ~34px home-indicator safe-area clearance (invisible/handled by Safari's own chrome in a browser tab, but the app's own responsibility once there's no more chrome) made the *total* visual gap read as much larger than on non-iOS or in a tab — so the user asked to shrink iOS's own design-gap portion specifically. Don't re-sync this constant back to match the CSS value; they're intentionally different now.
- **`.sheet-panel` gets the exact same iOS-only fixed-position fix as `#tabbar` (round 24)** — same shape of CSS rule (`position:fixed; bottom:0; height:50%`), so it's reasonable to expect it misbehaves for the same reason in iOS standalone mode. `positionSheetForIOS()` overrides `bottom:0; height:50%` with an explicit `top`/`height` in px computed from `--app-height`, iOS-only, called from `openSheetTransition()` (when a sheet first mounts) and from `onViewportChange()` (so it stays correct across a resize while open). Never runs anything if no `.sheet-panel` is currently mounted — cheap to call unconditionally.
- **The Stays detail view fully opens with the same box-morph-and-3D-flip animation the day deck uses, not a bottom sheet (round 24)** — `openStayFlip()`/`closeStayFlip()`, modeled directly on `openDayFlip()`/`closeDayFlip()`. The old bottom-sheet path for stays (`state.sheetAbout='stay:'+id`) is gone entirely — `sheetHTML()` only ever renders a day-chapter's About panel now.
- **The segmented control's selected-tab pill is a separate sliding element (round 24), not a background color on the active button** — `#tabbarIndicator` (a `span` sibling of `#tabExplore`/`#tabStays`, absolutely positioned behind them via `z-index:0`) transitions its own `transform:translateX(...)` between the two button slots; `.tabbar-btn.on` now only changes text color (`#fff`), not background. `render()` and `closeDayFlip()`/`closeStayFlip()`'s `finishClose()` all toggle `.right` on it in lockstep with `#tabExplore`/`#tabStays`'s own `.on` classes — if a future screen/tab is added, this needs the same three-way sync, same as the existing `.on`-class bug class documented above.

The user supplied their own `cards.svg`/`stays.svg` (pushed to the repo root, same folder as `index.html` — the CSS references them as bare relative filenames).
