## Design & Interaction Contract — fixed rules (read BEFORE touching UI/animation)
These were each arrived at after multiple rounds of iteration and user feedback. Don't change them without being explicitly asked to revisit them:
- **Type scale is 16px regular / 14px small / 12px bold uppercase for labels — nothing smaller than 14px except that third label tier** (round 4). Big headings (day titles, 20–25px) are unaffected. Rule of thumb: long-form readable copy (chapter blurbs, "about" text, teasers directly under a heading, tomorrow/locked-day notes) is 16px; secondary/meta/button text (dates under headings, prep values, buttons, confirm rows) is 14px; small all-caps eyebrows, tags and pills (chapter tags, prep-cell labels, "chapters"/"tomorrow" section labels, the card's bottom date line, hourly-forecast time ticks) are 12px + `font-weight:700` + uppercase. Don't reintroduce anything under 14px outside that labeled third tier.
- **Side margins between content and the device edge are 24px everywhere** (round 4) — the page-level horizontal padding/margin on `.dayhead`, `.backhero-text`, `.lockednote`, `.prep`, `.chapters`, `.tomorrow`, `.journalflag`, `.lastupdate` and the home hero was standardized from a mix of 16/17/20px to a single 24px. The stack-card's own internal photo-caption padding (17px, inset from the *card's* edge, not the device's) is a separate, unrelated value and was left alone.
- **The home screen's top hero is a centered red circle mark + "Japan Slowly" wordmark + trip date range** (round 4), replacing the old left-aligned wordmark-only header — and the demo-preview description line beneath it ("Preview state: evening of Day 2...") was removed entirely, not just hidden. `.home-hero` in index.html.
- **Deck cards only show a status pill when locked** (round 4) — journal/"in progress" (unlocked) cards no longer carry any status label. The trip-position indicator ("Day 2/10") that used to sit in a top-right badge now lives after the bottom date instead — **date/day-of-week first, then the count** ("SAT 26 SEP · Day 2/10", reordered round 7 from an earlier "Day 2 / 10 · SAT 26 SEP"); there is no separate top-right badge anymore.
- **The home hero mark is the user's own icon artwork, not a plain CSS circle** (round 5, updated round 6) — two PNGs (`MARK_LIGHT`/`MARK_DARK`, embedded as base64 in `index.html`), swapped with the same `prefers-color-scheme`/`data-theme` pattern the rest of the token system uses. Round 6 replaced both with transparent-background versions the user supplied (black text for light mode, white text for dark mode) — the mark now blends directly into the page instead of sitting in a visible opaque square, which is why `.home-hero .mark img` no longer has a `border-radius`/`object-fit:cover` clip (nothing to trim once there's no background fill). `icon-512.png` (the installed-app icon / `apple-touch-icon`) intentionally still uses the round-5 **opaque** light variant, not this transparent one — installed home-screen icons render badly with real transparency (iOS in particular fills transparent areas with an unpredictable backdrop), and a static manifest icon can't theme-swap the way the in-page mark does anyway. Don't regenerate/replace either without keeping both a light and dark variant supplied, and don't swap the transparent artwork into `icon-512.png`.
- **Home-hero vertical spacing is deliberate, not arbitrary** (round 5, tightened round 7): the hero's top padding is `calc(env(safe-area-inset-top, 0px) + 24px)` — not a flat pixel value — specifically so it clears the iPhone notch/Dynamic Island (which round 3 already learned only ever shows up on a real device). Round 7 replaced the hero's uniform flex `gap` with specific per-pair margins: mark→wordmark 4px, wordmark→range 2px. The hero's own bottom padding is 0; the gap down to the top of the card stack (40px as of round 7, was 48px in round 5) is owned entirely by `.stack-wrap`'s `margin-top` instead, so the two don't stack into something bigger than intended. Don't add padding to `.home-hero`'s bottom edge without correspondingly shrinking `.stack-wrap`'s margin-top.
- **`.dayhead` (the day-detail header, holding the back button) also needs `env(safe-area-inset-top)`** (round 7) — without it, the back button sat directly under the iPhone status bar/clock, sometimes fully unreachable under it. Same pattern as the home hero and `.refresh-fab`.
- **`.stack-wrap` sizes itself with `flex:1 1 auto`, not a fixed percentage** (round 7, was `flex:0 0 66%` since round 1) — a fixed percentage of the deck plus the hero's own (now variable, safe-area-dependent) height could together exceed the screen height on a real device/shorter viewport, forcing `.view` to scroll. Don't revert to a fixed flex-basis without re-testing on a short viewport with a large safe-area-inset-top.
- **`.stack-wrap` also carries `margin-bottom:48px`, reserved space for the front card's box-shadow to bleed into** (round 8) — this is a *separate* fix from the `flex:1 1 auto` change above, for a different symptom. Even with no page-level scroll, the shadow was still getting hard-clipped at `.view`'s bottom edge, because a `.stack-card`'s `top:50%/height:100%` positioning is relative to its containing block, which for an absolutely-positioned element **includes its parent's padding** — so `.stack-wrap`'s own `padding-bottom` creates zero usable slack below the card; the card's box always extends to stack-wrap's exact outer edge regardless of that padding value. The only way to give the shadow real room is genuine empty space *below* stack-wrap's own box, which is what this margin reserves. flexbox still correctly subtracts a flex item's margins from what `flex:1 1 auto` treats as "remaining space," so the page still never needs to scroll. 48px comfortably covers the shadow's `0 22px 40px -18px` spec (~44px of visible bleed). If the shadow's offset/blur/spread values ever change, re-check whether 48px is still enough headroom — don't assume it scales automatically.
- **Deck cards are `width:min(320px, 82%)`, not a flat 300px** (round 8) — widened 20px on request. At most viewport widths this hits the 82% cap rather than the 320px ceiling, so the practical effect is similar to raising the old 300px cap, not a fixed +20px on every device.
- **Opening a card synchronously snaps it to its resting front-card transform (`scale(1) rotate(0)`) before measuring its "from" rect, AND that snap's `transition:none` must be cleared back to `''` immediately after** (round 4, regression fixed round 7, `openDayFlip` in index.html). The snap-before-measure fixes a real bug where tapping the newly-focused card immediately after a swipe (before its .6s snap-into-focus transition finished) measured it mid-transition but then sized the "from" box using its resting (unrotated, unscaled) layout size, so it visibly popped to full size right as the open animation began. Closing-then-reopening never showed this because the card was always already settled by then. Don't remove this snap-before-measure step without retesting the swipe-then-immediately-tap case specifically — a delayed tap after the swipe settles won't reproduce it. **But** leaving that snap's `cardEl.style.transition = 'none'` in place afterward is a *different*, worse bug: an inline `style.transition` always out-ranks a class-based transition rule regardless of add order, so it silently cancelled the `.opening` class's own top/left/width/height transition for the rest of the function — every open looked like an instant jump to fullscreen size with only the flip's rotateY still animating. Round 7 added `cardEl.style.transition = '';` right after the forced-reflow flush to clear it. If this class of bug resurfaces, check every place that sets `el.style.transition` directly for a matching reset later in the same flow.
- **The home-reel drag zone needs `touch-action:none` on `.stack-wrap`, and `html`/`body` need to be locked from ever scrolling/bouncing** (round 3): a real phone was the only way this surfaced — desktop mouse/trackpad testing never showed it. With `touch-action:pan-y` (the original value) a real finger drag is never perfectly horizontal, so the browser's own vertical-pan gesture kept hijacking the custom drag as a native scroll/bounce, fighting the JS handler. Separately, `html`/`body` had no `overflow`/`overscroll-behavior` rules at all, so the whole document itself could pan and rubber-band in both directions even though `.screen` internally has `overflow:hidden`. Fixed with `touch-action:none` on `.stack-wrap`, `html,body{overflow:hidden;overscroll-behavior:none}` + `body{position:fixed;inset:0}`, and `overscroll-behavior:contain` on `.view` (the one element that's *supposed* to scroll, for a day's detail content). Don't reintroduce `pan-y` or drop the html/body lock without testing drag on an actual phone afterward — this class of bug doesn't show up any other way.
- **Design tokens are ported from the `leve` project's design system** (round 2): the `:root` block in `index.html` uses the same semantic roles leve uses (surface/content/border/accent, light+dark remap via `prefers-color-scheme` and a `data-theme` override) and the same Outfit typeface everywhere, replacing the original Fraunces/Work Sans/IBM Plex Mono mix. The one deliberate divergence: **the accent hue is a torii-red (`#d6432e` light / `#ff7a61` dark), not leve's mint** — chosen specifically to keep a Japan-flavored identity instead of reading as a re-skinned iOS app. Variable *names* (`--bg`, `--ink`, `--accent`, etc.) were kept unchanged from the pre-round-2 file so no other rule needed touching. Don't silently revert to the old warm/paper palette or reintroduce the three-font mix without being asked.
- **Card jitter range is 1–3°**, applied only to non-front deck cards (`CARD_JITTER` array in index.html). A wider 3–5° range was tried and explicitly rejected as "too much."
- **The front/focused card has NO tilt** (`rot:0` at offset 0). Adding one was tried, then explicitly reverted — it interacted badly with the deck-movement animation. Don't re-add without the user raising it again.
- **Open/close uses a combined 3D flip + FLIP-technique box-morph** (animating top/left/width/height, not `transform:scale`), specifically so photo/text proportions never distort. This is why the code reparents the card into `#screen` and manually computes pixel rects instead of using simpler CSS.
- **The rest of the deck gathers into a tidy, square, untilted stack while one card is open/closing**, then spreads back into its natural fan as the card lands. This exists specifically to mask the fact that a rotated card can't gracefully unrotate into a tilted slot on its own — it's a workaround, not a feature in its own right.
- **Card shadows fade via `box-shadow` transition only, never via opacity** — fading the whole card was tried and rejected ("makes the cards behind disappear").
- **The drag-release snap uses a gentle spring/overshoot curve** (`cubic-bezier(.34,1.56,.64,1)`, .6s — round 3), not a plain ease-out. The original curve decelerated almost immediately, so nearly all the motion happened in the first sliver of the transition and read as an abrupt snap regardless of duration; the spring curve settles slightly past rest before easing back, which reads as a natural physical "landing." This is specifically for the drag-to-browse release on the home reel — NOT the day open/close flip below, which is a separate, independently-tuned animation.
- **On close, the animated card element is folded directly into the deck as the permanent front card, not destroyed and rebuilt via a full `render()`.** This was a real bug (a one-frame subpixel "shimmer" from swapping a continuously-animated element for a freshly-laid-out one) — don't reintroduce a full-rebuild-on-close pattern.
- **The outer "gallery" demo chrome (title/description header, decorative side dots, phone-bezel mockup) has been removed.** The page is meant to be opened directly / installed as a home-screen app, so it should always just BE the app, full-bleed — don't reintroduce a phone-simulation wrapper.
- **A "jump" that looked like a real animation bug turned out to be a Safari-in-webview rendering quirk specific to the claude.ai chat's in-app preview** — confirmed fine in real Chrome and standalone Safari. If something like this comes up again, reproduce it in an actual browser (not the chat preview) before spending time on it. (Round 3 reinforces this: several real bugs — the touch-action conflict, the missing viewport tag — likewise only ever showed up on an actual phone, never in desktop testing. Always verify anything drag/touch/scroll-related on a real device before concluding it's fine.)
- **No real, named public figures or copyrighted film/show branding in any generated imagery** (a stylized "Lost in Translation" poster with Bill Murray/Scarlett Johansson was declined for Day 2; the user's own uploaded photo was used instead).
- **App opens on a full-screen intro/splash view (`state.screen==='intro'`), not directly into the home carousel** (round 9) — mark, "Japan, unscripted" title, date range, and a "Start your journey" CTA (`.intro-cta`), sharing the same `heroMarkupHTML()` markup as the compact home hero so the two states can FLIP-morph between each other cleanly. Tapping the CTA calls `goHome()`: a FLIP transform on `.mark` (`markMorph`) from its large intro size/position to its small home position, while the wordmark/date/CTA cross-fade out and the deck cross-fades in underneath. Tapping the home view's hero (`.home-hero`, wired in `wireHome()`) calls `goIntro()`, which reverses the same FLIP. Don't naively CSS-`transform:scale()` the whole hero block for this — the intro title wraps to two lines and the home title is one line, so a scale-morph of the full block would visibly reflow/distort text; only the visually-identical `.mark` icon is FLIP-morphed, everything else cross-fades.
- **Icon references carry a cache-busting `?v=N` query string** (`manifest.json`'s two icon entries and the `<link rel="apple-touch-icon">` in `index.html`, currently `?v=9`) — round 9 fix for the app icon silently not updating. Browsers/OS cache an installed PWA icon very aggressively by exact URL, and `icon-512.png` had been swapped twice before (rounds 5 and 6) with the filename unchanged, so nothing ever told the OS a new copy existed. Bump this query param any time `icon-512.png`'s actual pixel content changes again. This only fixes it going forward for a *fresh* fetch/install — an icon already on a phone's home screen was cached at install time and needs a manual remove-and-re-add of the app to pick up a new one; there's no way to force that remotely.
- **The deck card animating INTO focus gets its own, slower, separate transition from the rest of the deck** (`applyStack()`, round 9) — `transform .85s cubic-bezier(.22,1,.36,1)` set as an inline style only on the card becoming the new front card, cleared back to `''` on that transition's `transitionend` so it doesn't linger and affect some later unrelated transform change on the same element (this is exactly the shape of bug the round-4/7 `transition:none` regression was — see that contract entry below — so the cleanup here is deliberate, not optional). The incoming card travels a much bigger transform delta (small tilted background card → full-size untilted front card) than the outgoing card does, which made it read as noticeably snappier even though both nominally shared the same `.6s` deck transition. Don't remove the inline-transition cleanup, and don't unify this back with the deck's shared timing without the user asking.
- **Accent red is `#E11401`** (round 9, was `#d6432e` from round 2) — light/dark hover variants (`--accent-soft`) and the dark-mode pair were re-derived proportionally (same HSL lightness/saturation offset from base as the old palette), not just eyeballed. Update `manifest.json`'s `theme_color` to match if this changes again.
- **Chapters are individual floating cards, not rows sharing borders** (round 10) — each `.chapter` has its own background/border/radius(16px)/shadow, with a real 16px gap between cards (was a single continuous block with `border-top`/`border-bottom` rules and a 10px first-pass gap). Card internal padding is `12px 16px` and the gap between the title+body block and the "About this place" link is 8px — these three numbers came directly from the Figma design's own dev-mode "Spacing" export (exact pixel values, not estimated), so don't nudge them without a reason to override that source. `.ctitle` is **16px/500 weight** and `.abouttoggle` is **14px/500 weight**, no leading icon — a first pass bumped these to 20px/700 and 18px/700 based on pixel-measuring the design screenshot, but the user then gave the exact spec directly ("outfit 16pt medium weight... the About this place 14pt medium"), which overrides the pixel-measured guess. Don't re-derive these from the screenshot again; the user's stated numbers are authoritative.
- **Gap between the "Last update" line and the "CHAPTERS" label is a fixed 40px** (round 10 set it to 24px, round 14 widened it to 40px) — `.chapters`'s `margin-top`. Requested as an exact value both times, not estimated.
- **`ch.about` can be either a flat `[label,value]` row list (original shape, unchanged rendering) or a list of named groups for a chapter whose About panel opens into several sub-places** (round 16) — `{group:'Place name', tag:'Priority A' (optional), rows:[[label,value],...]}`. `aboutItemsHTML()` in index.html detects which shape it got by checking whether the first entry is a 2-element array (flat) or a plain object (grouped); mixing the two shapes within one chapter's `about` isn't supported. Currently grouped: `shibuya` (6 places), `harajuku` (5), `omotesando` (3). Still flat: `pasela`, `nightlife`, and Day 1's chapters. Don't collapse this back to a single shape without checking every chapter that currently relies on the flat form.
- **The chapter timeline (dot + dashed connector) lives OUTSIDE the card, not inside it** (round 10, corrected mid-round after the first pass left it nested inside the card the way it always had been pre-redesign) — `.chaprow` is a flex row of `.timeline` (32px column, narrowed from 48px in round 13) + `.chapter` (the card) as siblings; `chapterBlock()` returns only the card's own content, and `chapterRowHTML()` wraps it with the timeline. This works without any JS height measurement because `.timeline` stretches to match the card's height via flexbox's default `align-items:stretch`. Dot state colors are classes directly on `.tl-dot` (`.tl-dot.revealed`, `.tl-dot.ontheway`) rather than `.chapter.revealed .cmarker`-style descendant selectors, since the dot is no longer inside the card it represents — don't reintroduce a descendant-selector pattern here, it'll silently stop matching. **The card sits a fixed 16px from the dot's center** (round 13, was 32px) — achieved by narrowing `.timeline` from 48px to 32px while giving `.tl-dot`/`.tl-line` a fixed `left:16px` (not a 50%-based calc), so the narrower column pulls the card closer without moving the dot itself.
- **`.tl-dot`/`.tl-line`'s `left` and `top` are fixed pixel values, not percentage-based** (round 12 shifted them 8px left, round 13 changed the basis entirely to fixed values, round 13 also changed `top`) — `left:16px` (was `calc(50% - 8px)` against the pre-round-13 48px-wide column, which itself was `calc(50% - 8px)` against the original 48px column before round 12's 8px-left request) and `top:18px` (was 24px) — the top value was empirically measured via Playwright (`getBoundingClientRect()` on `.ctitle` vs. `.chapter`) to land the dot's own vertical center exactly on the chapter title's line-box center, not eyeballed. If the card's padding-top (currently 12px) or `.ctitle`'s font-size (16px) ever change, re-measure this rather than assuming the same 18px still centers correctly.
- **`.tl-dot` carries a 4px solid background-color halo** (round 11, `box-shadow:0 0 0 4px var(--bg)`) — so the dashed `.tl-line` passing behind it visibly stops short of the dot with a gap, instead of appearing to run directly into it. This is layered on top of the round-10 fix below (solid dot fill instead of transparent) — the halo is an *additional* ring outside the dot's own circle, not a replacement for the fill.
- **`.tl-line` deliberately overshoots into each dot's center on both ends, not just up to its edge** (round 10, fixed after a visible gap was reported) — `top:18px` (this row's dot center, per the round-13 re-measurement above) and `bottom:-34px` (next row's dot center: `.chaprow`'s 16px margin-bottom + the next dot's own 18px top offset — recalculated in round 13 when the top offset changed from 24 to 18). `.tl-dot` carries `z-index:1` specifically so it paints over that overlap cleanly. Don't "fix" the overshoot by trying to land exactly on the dot's edge instead — that's fragile to any future change in dot size, which this approach isn't. **`.tl-line` also carries `margin-left:-1px`** (round 10, third post-delivery fix, per the user's literal "1px to the left") — a `border-left` on a zero-width absolutely-positioned box paints starting AT its `left` edge extending rightward, not straddling a center point, so without this the 2px dash sat ~2px right of the dot's true center; the negative margin shifts the whole box left by half the border width so the dash strip is centered on the dot instead of offset from it. If `.tl-dot`'s `top`/`.chaprow`'s margin-bottom/the column width ever change again, recompute both this `bottom` value and the two entries above together — they're derived from the same three numbers.
- **Chapter timeline dots are two states now, not three** (round 10) — filled red (`.tl-dot.revealed`) or an outline (default/hidden = grey `--ink-faint` border, `.tl-dot.ontheway` = red `--accent` border). The previous half-filled gold `repeating-conic-gradient` treatment for "on the way" was explicitly rejected in favor of the simpler red outline — don't reintroduce a third fill treatment without being asked. **Both outline states carry a solid `background:var(--bg)`, not `transparent`** (round 10, third post-delivery fix) — the dashed `.tl-line` passes directly behind every dot, and a transparent-fill outline dot let the dash show through its center; matching the dot's background to the page background hides that cleanly. If `--bg` is ever set to something non-opaque or the dot is placed over a non-`--bg` surface, this technique needs revisiting.
- **Locked/not-yet-revealed chapter cards (`ch.state==='hidden'`, rendered as "Hidden") have no box-shadow** (round 13, `.chapter.hidden{box-shadow:none}`) — reads as visually flat/inert next to the revealed and on-the-way cards, which keep the standard `0 2px 10px rgba(0,0,0,.05)` shadow.
- **The gap from the day-detail header down to the weather/day-info card (`.prep`) is a fixed 16px** (round 14, was an unintentional 32px — `.backhero-text`'s own 16px bottom padding plus `.prep`'s separate 16px `margin-top` were stacking) — `.prep`'s `margin-top` is now 0, so the 16px comes entirely from `.backhero-text`'s existing padding. On the journal-day path, where `.journalflag` sits between the header and `.prep`, `.journalflag` was given its own `margin-bottom:16px` specifically to preserve that path's spacing unchanged by this — if you touch either of these two margins again, check both paths (a day with `status:'journal'` and one without).
- **The day-detail header has no horizontal rule under the teaser text** (round 10) — `.backhero-text`'s `border-bottom` was removed. This is the one page-level divider that existed in that view; `.prep`'s own internal grid lines (`.prep-cell`, `.hourly`) are unrelated and untouched (still explicitly unstyled — see the `.prep` contract entry above). Also removed entirely: the day2-specific "In progress · N of M chapters revealed" label. The `isJournal` "past day" label is a separate line and was left alone.
- **"Last update" is computed, not hardcoded text** (round 10) — `formatLastUpdate(appLoadedAt)` renders "Today, HH:MM" (24h) when `appLoadedAt` (stamped once at app load, standing in for "when content was fetched" since there's no real backend) falls on today, or just "Yesterday" / "N days ago" (no time) otherwise. In practice this will almost always show "Today, HH:MM" in any live demo, since `appLoadedAt` is always "now" — the older-day branches exist for correctness, not because anything currently exercises them.
- **"About this place" opens a bottom-sheet modal, not an inline expand/collapse accordion** (round 10) — `state.sheetAbout` holds the open chapter's id (or `null`); `sheetHTML()` renders the sheet as a *sibling* of `.view` (not a child — it must never be clipped by `.view`'s own `overflow-y:auto` box) inside `render()`. Opening is a same-screen re-render, so the `render()` scroll-preserving fix (see below) is what keeps the page underneath from jumping when it opens. Closing runs the reverse transition first (`closeSheet()` strips the `.open` classes, waits for the panel's `transitionend` on `propertyName==='transform'`) and only *then* clears state and re-renders — flipping state immediately would let `render()` throw the animating DOM away before the close transition ever painted. Don't wire a new sheet-closing path that skips this.
- **`render()` preserves scroll position across a same-screen re-render** (round 10) — it used to rebuild `.view` from scratch on every `render()` call (revealing a chapter, confirming an arrival, opening the sheet, etc.), and a freshly-created element always starts at `scrollTop:0`, so any of those actions used to visibly snap the page back to the top. Each rendered `.view` now carries `data-screen-key="<screen>:<openDay>"`; `render()` only restores the previous `.view`'s `scrollTop` when the new one's key matches, so a genuine navigation to a different screen/day still correctly starts at the top. If you add a new same-screen state change that calls `render()`, this fix already covers it — no per-caller change needed. If you add a new *screen*, make sure `state.screen` (and `state.openDay` where relevant) actually changes for it, or this key comparison won't tell it apart from the screen it's replacing.
- **`.prep` (the weather/day-details block) has a light grey background and nothing else has been designed yet** (round 10) — uses `--frame` (`#f7f6f9` light / `#161618` dark), a token that was already defined in `:root` but unused until now. Its light-mode hex was tuned to match a pixel sample of the Figma mockup's grey box; the dark-mode value is untouched since there's no dark-mode reference to match. Don't restyle the rest of `.prep`/`.weather-cell`/`.prep-cell` beyond this without the user asking — it's explicitly still a placeholder. **The last row's cells have no `border-bottom`** (round 10, third post-delivery fix: `.prep-row:last-child .prep-cell{border-bottom:0}`) — removes the stray separator line that used to sit between the bottom of the grid and the block's own outer border/rounded corner. The internal vertical/horizontal grid lines between cells elsewhere in `.prep` are untouched.
- **`.tomorrow` (the bottom "what's next" card) shares `.prep`'s background** (round 11, `background:var(--frame)`) — was unstyled/transparent in its default dashed-border state and `--bg-elevated` in its solid "ready" state; both now use `--frame` so the day-detail view's two bookend cards read as a matched pair. `.tomorrow.ready` still switches `border-style` from dashed to solid, just no longer also switches the background.
- **`icon-512.png` is a standalone square icon, deliberately not reusing `MARK_LIGHT`/`MARK_DARK`** (round 15) — round 15 discovered that despite changelog entries for rounds 5/6/9 describing this file as swapped to the user's mark artwork, the committed PNG had never actually changed since the round-1 placeholder gradient; separately, `manifest.json`'s two icon entries had no cache-busting query string at all (only the `apple-touch-icon` `<link>` did), so even a correctly-updated file could stay stuck on platforms that read the manifest's icon list instead of that link. Round 15 fixed both: replaced `icon-512.png` with the user-supplied artwork (black background, solid red circle, white "スローリーニホン" wordmark — fully opaque, safe for both `any` and `maskable` manifest purposes), and added `?v=10` to every icon reference (manifest's two entries plus the apple-touch-icon link), keeping them all in sync going forward. Also synced `manifest.json`'s `theme_color` from the stale `#d6432e` (round 2's accent) to the current `#E11401` (round 9's accent), which had been flagged but never actually fixed. As always, an icon already on a phone's home screen needs a manual remove/re-add to pick up the change — no remote fix for that. See Known Gaps for the still-open maskable-safe-zone caveat on this new artwork's text.
- **The app's own displayed name is "japan, slowly…", lowercase, with the ellipsis** (round 17, was "Japan, unscripted" from round 9, itself replacing the original "Japan Slowly") — every user-visible spot updated together: `<title>`, the `apple-mobile-web-app-title` meta tag, `heroMarkupHTML()`'s wordmark markup (shared by the intro splash and the compact home hero, so both update from one place), and `manifest.json`'s `name`/`short_name`. `icon-512.png`'s own embedded wordmark artwork and internal code comments referencing older names were deliberately left alone — this was a copy change, not a mark/branding redesign. If the name changes again, update all four of those together, not just the visible page title.
- **`.close-fab` (day-detail screen) replaces the old back-arrow/"The Reel" button** (round 17) — a `position:fixed` X-in-a-circle, top-left, mirroring `.refresh-fab`'s own recipe (size/shape/shadow/`env(safe-area-inset-top)`) in the opposite corner, wired to the same `data-back` → `closeDayFlip()` handler. Unlike `.refresh-fab`, which is a persistent sibling of `#screen` needing its own manual `[hidden]` toggle in `render()` (see the reload-button entry below), `.close-fab` is rendered as part of `dayDetailScreen()`'s own HTML and simply isn't present when `render()` builds any other screen — don't add manual show/hide bookkeeping for it, it doesn't need any. `.dayhead` is still rendered on every day screen (not just when a reset button needs it) purely for its own `env(safe-area-inset-top)` padding — that's what actually clears the status bar/notch for the title/teaser text below it, independent of whatever's inside the row itself.
- **`#refreshBtn`'s `[hidden]` toggle must be kept in sync with every code path that can land on `state.screen==='home'`, not just `render()`** (round 17, real bug fix) — `render()` is the only place that ever sets `refreshBtn.hidden`, but `closeDayFlip()`'s `finishClose()` deliberately returns to the home screen WITHOUT calling `render()` (round 1's fold-the-card-in-directly fix, to avoid a shimmer — see that contract entry below), which is also the one path every actual "go back" tap takes. `finishClose()` now sets `refreshBtn.hidden = false` itself, mirroring `render()`'s rule (`state.screen` is always `'home'` by the time it runs) instead of calling `render()`. If a future round adds another way to land on `home`/`intro` without going through `render()`, it needs this same explicit line, or the button will silently stay hidden forever after the first day-detail visit again.
- **`.view` gets extra `padding-bottom` only on the day-detail screen, via a `view-day` modifier class** (round 17, real bug fix — content was reading as cropped ~60px from the bottom on a real iPhone) — `.dayhead`/`.sheet-panel`/the home hero all already account for `env(safe-area-inset-*)` on whichever edge touches the notch/Dynamic Island/home-indicator, but `.view` (the one element that actually scrolls) never did on its bottom edge, so the last content above the safe-area boundary read as clipped with nothing reserving room past it — invisible in desktop/Playwright testing, which has no safe-area inset to miss. `render()` adds `view-day` to `.view`'s class list only while `state.screen==='day'`; `.view.view-day{ padding-bottom:calc(env(safe-area-inset-bottom, 0px) + 24px); }`. Deliberately scoped to the day screen, not applied globally — the home/intro `.view` never scrolls, and `.stack-wrap`'s own bottom margin (round 8's shadow-bleed fix) is a separate, already-tuned value that shouldn't stack with this.
- **The About sheet can be dragged down to dismiss it** (round 17) — `wireSheetDrag()`, wired every time the sheet mounts (same call site as `openSheetTransition()`). A drag can start from `.sheet-handle`/`.sheet-header` unconditionally, or from `.sheet-body`'s own content but ONLY when it's already scrolled to `scrollTop:0` — the decision is deferred to the first real pointermove (a `pending` flag) rather than decided at pointerdown, since at that instant being scrolled to 0 doesn't yet say which way the user's about to drag. While active, `.sheet-panel`'s `transform` and `.sheet-backdrop`'s `background` are both driven directly with `transition:none` for 1:1 tracking (the same technique `wireHome()`'s card-drag already uses), with light resistance on any upward overshoot past fully-open. On release: past either a 28%-of-panel-height distance threshold or a velocity threshold, it slides out and closes (driven inline, the same "inline always outranks class" fact the round-4/7 regression is about, used deliberately here since a class toggle alone can't override an already-set inline transform); otherwise it snaps back open. Either way, every inline override this sets gets cleared back to `''` once the settle transition ends, so the plain `.sheet-panel.open`/`.sheet-backdrop.open` class rules fully govern the sheet again afterward — don't leave an inline `transform`/`background`/`transition` lingering past that point, or `closeSheet()`'s own classList-based close (used by the X button and backdrop tap) will silently stop working the next time, exactly the class of bug the round-4/7 entry warns about.
- **The About sheet's header is a 3-column grid, close button fixed-left, title centered against the panel — not the button** (round 17, was a flex row with the title on the left and the close button on the right) — `.sheet-header{ grid-template-columns:32px 1fr 32px; }`, `.sheet-close` pinned to the first column, `.sheet-title` centered in the middle one. Both outer tracks are fixed to the close button's own 32px footprint specifically so the title's center lines up with the panel's true center regardless of title length — a plain flex `justify-content:space-between` would only center it relative to whatever width the button happens to be, not the panel. `.sheet-close` is now a filled circle (`background:var(--frame)`) rather than a bare icon, reading as a proper modal dismiss control.
- **A chapter's About panel with more than one place renders as a one-at-a-time collapsed accordion, not all-expanded** (round 17) — only kicks in once `ch.about` is the grouped shape AND has more than one group; a single group (nightlife's MITSUKI-only panel) still renders plain and always-expanded, since there's nothing to choose between. Each collapsible row's open/closed state lives purely in the DOM (a `.about-group.collapsible.open` class + a measured inline `max-height` on `.about-group-collapse`, toggled directly in `wireCommon()`'s `data-group-toggle` handler) rather than in `state` — deliberately, so it doesn't force a full `render()` (and the fresh, already-in-its-final-state DOM node that would produce, with nothing to visibly animate from) every time someone taps a row. Opening one collapses whichever other row in the same sheet was open. `max-height` is measured from the row's actual `scrollHeight` at toggle time, not a fixed guessed number, so the transition duration reads consistently regardless of how much text a given place has. Opening a row also scrolls `.sheet-body` so that row's own header lands near the top of the sheet's visible area (computed via `getBoundingClientRect()`, not `offsetTop`, at click time — the tapped row's own position doesn't move as its content grows below it, so this doesn't need to wait for the expand animation to finish). A freshly (re)opened sheet always starts fully collapsed, since `render()` rebuilds the sheet's DOM from scratch on every open.

## What We're Building
Full product vision: see README.md (short) or `docs/Japan Slowly - Product Concept v2.docx` (full, includes its own zero-context Appendix A). One-line version: a spoiler-light PWA for a 3-person Japan trip (25 Sep–4 Oct 2026) where two travellers experience each day progressively instead of reading the full itinerary up front, while the planner has a separate operational Guide Mode.

## Current Scope (this prototype)
- Explorer Mode only. Guide Mode does not exist yet, not even a stub.
- Only Day 1 and Day 2 have real detail screens; Days 3–10 exist only as locked cards in the deck.
- All content (itinerary text, chapter data, "About this place" copy, weather numbers) is hardcoded in `index.html`. No API calls, no backend, nothing persists across a page reload.
- No automated tests. Verification so far has been manual/visual (Playwright screenshots + frame-by-frame video diffing during debugging, plus real-device testing on the user's phone starting round 3), not a real test suite.
- Live at `https://everydayou.github.io/japan-slowly/` via GitHub Pages (round 3) — can be installed to a phone home screen from there.

Fixed all three (viewport meta tag; `touch-action:none` + full html/body scroll lock with `overscroll-behavior`; `.view` given `overscroll-behavior:contain` so its own legitimate internal scroll doesn't chain up into a body-level bounce). Separately, reworked the drag-release snap animation from a front-loaded ease-out to a gentle spring/overshoot curve per user feedback that it "didn't feel natural" — the real issue was curve shape, not duration (a first attempt at just slowing it down wasn't perceptibly different). Added an in-app reload button (top-right of the home reel) so the user can force-fetch the latest published version without needing browser chrome, which a standalone installed home-screen app doesn't have. All changes verified with Playwright (including iPhone touch/viewport emulation) before handoff; user pushed each change from their own machine, including switching to a Personal Access Token for git auth on a second (new) computer partway through the round.
